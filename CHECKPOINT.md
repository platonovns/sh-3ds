## Что восстановлено и почему

На момент аудита в интеграционном checkout не было staged изменений и отличий игровых source/build файлов, видимых обычному `git status`: имелись 17 изменённых JSON-отчётов и 22 неотслеживаемых файла (16 отчётов, журнал и пять build outputs). Эти отчёты и outputs не являются входами к игровой сборке и не переносились в commit. Игнорируемые `build/`, `build-game/` и `__pycache__/` — generated cache и объекты; новый checkout собирался без этих каталогов. Единственная выявленная побайтовая разница 1 131 входа `build_identity.py` — CRLF в самом последнем переводе строки `3ds_port/source/game_lower.c` и `school_anim_relocate.c`: Git считала эти изменения чистыми вследствие нормализации строк. Исходный порт и чистый checkout в остальном совпали побайтово в пределах этого списка; compiler/link проверка дополнительно охватывает необходимые входы за пределами списка. Атрибуты `-text` и эти два файла включены в checkpoint с оригинальными байтами; смысл C-кода не менялся. Build ID хеширует именно исходные байты.

`pc_port/PsyCross` — настоящий submodule, зафиксирован на `9f74c4c314251a7ed04d8c7e5906c782f0b342c7`; содержимое используемых в identity файлов в интеграционной копии совпадало с закреплённым. Готовый исходный код maps, generated таблицы `pc_port/build_gen/extracted_data`, `stage11a_b` и скрипты генерации находятся в Git; стандартные временные outputs формируются при сборке. Проверять наличие submodule перед сборкой. Не включать оригинальные игровые диски, сохранения, приватные hardware uploads и локальные caches в Git.

Историческое дерево `silent-hill-decomp`, `codex/stage11a-cpu` на `7d08d12273d85e086f74aeac83a2d9f072348945`, содержит 116 изменённых отслеживаемых путей и 2 733 неотслеживаемых файла; staged изменений при аудите не было. Это предыдущее состояние, не источник для нового игрового checkout. В частности, среди неотслеживаемых находятся исходники/тесты/инструменты, архивы прежних baseline и многочисленные hardware reports; не стирать и не считать их мусором. В этой ветке сохранены непосредственно нужные серверные файлы, инструмент приёма hardware reports и несколько исторических документов. Не все исторические ссылки в них разрешаются внутри этого checkpoint; полные исходные отчёты остаются в старом дереве. Там же игнорируются `sh1_data`, published бинарники, build outputs и runtime server. ## Сборка и доставка

Установить devkitPro с devkitARM, libctru, Citro3D, 3dstools и picasso, GNU make, Python 3, patch и обычные shell tools. Проверенная конфигурация: devkitARM r68 / GCC 16.1.0, binutils 2.46.0, newlib 4.6.0.20260123-5, rules 1.6.0-4, libctru 2.7.0-1, citro3d 1.7.1-2, 3dstools 1.3.1-3, picasso 2.7.2-3; Ubuntu 26.04, make 4.4.1, Python 3.14.4. На другом SDK воспроизводимость байтов не гарантируется.

Из devkitPro shell, в корне checkout:

```sh
export DEVKITPRO=/path/to/devkitpro
export DEVKITARM="$DEVKITPRO/devkitARM"
export PATH="$DEVKITPRO/tools/bin:$DEVKITARM/bin:$PATH"
cd 3ds_port
make -f Makefile.game -j8
```

Команда запускает prepare, компиляцию, link, упаковку и обязательную публикацию. Она создаёт `3ds_port/silenthill_game.3dsx`, `.elf`, `.smdh`, `.map` и генерирует файлы в `3ds_port/build/`, `build-game/` и некоторые отчёты в `reports/`. При обычной проверке не запускать `make clean` на существующих данных. Для WSL на исходном ПК использовалась команда в `HANDOFF.md`; пользовательский SDK расположен в `.toolchain` соседней рабочей папки и не входит в Git.

При WSL публикация использует Windows Python: найденный bundled runtime пользователя или доступный `python.exe`; при необходимости передать путь Windows Python в форме WSL через `SH_3DS_WINDOWS_PYTHON`. Скрипт выбирает старый соседний `silent-hill-decomp/3ds_port/dev_server`, если он есть, иначе сервер в этом checkout. На Windows `SH_3DS_SERVER_DIR` позволяет явно указать каталог сервера; при вызове из WSL переменную следует передавать в Windows окружение через `WSLENV`, предварительно преобразовав путь. Скрипты сервера включены в checkpoint. На исходном ПК опубликованный каталог остаётся `silent-hill-decomp/3ds_port/dev_server/published`: именно он закреплён пользовательским правилом. Если сервер уже обслуживает другой каталог, он не останавливается и доставка сообщает об ошибке. Везде после новой успешной игровой сборки необходимо опубликовать файл на ПК пользователя, проверить по HTTP manifest/размер/SHA-256, оставить сервер работающим; вне этой сети/на другом ПК нельзя объявлять доставку выполненной без реальной проверки. Если нужны иные пути/адреса, согласовать их с пользователем. См. `3ds_port/dev_server/README.md`; абсолютные пути в исторических примерах относятся к исходной машине.

Для игры на SD отдельно требуются собственные `sdmc:/3ds/silenthill/sh1.bin` и `sh1.cue` версии USA SLUS-00707 v1.1, а также сохранения при необходимости. Их нет в Git и bundle; получить у пользователя законно, не пересылать вместе с открытыми исходниками. BIN для runtime; сборка кода в этой проверке использовала имеющиеся в checkout C-таблицы и submodule, не копируя диск в `.3dsx`.

## Как открыть на новой машине

Из Git-репозитория, где передана ветка:

```sh
git clone --no-checkout <repository-url-or-bundle> silent-hill-3ds
cd silent-hill-3ds
git switch --track origin/handoff/playable-after-sewer
git submodule update --init pc_port/PsyCross
git status --short --branch
git rev-parse HEAD
```

Проверить, что HEAD соответствует переданному финальному commit и submodule — `9f74c4c314251a7ed04d8c7e5906c782f0b342c7`. В offline-комплекте два bundle. Проверенный пример из PowerShell: сначала скопировать каталог `handoff-reference` на новую машину, затем выполнить (заменить абсолютные пути):

```powershell
git clone --no-checkout 'C:/path/handoff-reference/silent-hill-playable-after-sewer.bundle' silent-hill-3ds
Set-Location silent-hill-3ds
git switch --track origin/handoff/playable-after-sewer
git config submodule.pc_port/PsyCross.url 'C:/path/handoff-reference/psycross-9f74c4c.bundle'
git -c protocol.file.allow=always submodule update --init pc_port/PsyCross
git submodule status pc_port/PsyCross
git status --short --branch
git rev-parse HEAD
```

Постоянная локальная настройка URL нужна для корректного `git submodule status`; это меняет только конфигурацию нового clone. Эти команды проверены на отдельном clone. Для последующих сетевых обновлений можно вернуть URL из `.gitmodules`. Другие submodules не нужны для проверенного игрового target; при работе над другими частями проекта инициализировать их по необходимости. Локальный reference `.3dsx` и manifest лежат в `handoff-reference/` вне Git, сохранить их и сверить SHA перед воспроизведением. Для физического теста использовать New 3DS; прохождение подтверждено пользователем до выхода из первой канализации, новые сборки требуют `NEEDS HARDWARE TEST`.
